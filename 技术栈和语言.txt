一、前端部分：Vue3 + Vite + Element Plus + Pinia + SSE
1. Vue 3

Vue 3是目前主流前端框架里体积小、上手曲线平缓的一个。和React相比，Vue的模板更接近HTML，用在中后台工具类页面上很合适。你的平台本质是一个“AI工作台”，不是面向海量用户的复杂社交应用，Vue 3完全够用。

2. Vite

Vite是构建工具，负责把你的Vue源码打包成浏览器能直接运行的静态文件。它有两个优点对你特别重要：

开发时响应快：豆包在写代码、调试时，屏幕上的热更新几乎是瞬时的，效率高。
打包产物小：最终生成的文件可以压缩得很小，加载快，而且它是纯静态文件，只由Nginx托管，不占Python进程的内存。
3. Element Plus

这是Vue3的UI组件库，提供按钮、表单、上传框、弹窗、表格、标签页这些现成控件。对你来说很重要的一点是：豆包对这套组件库非常熟悉，它能直接写出漂亮的界面，不用从零去造轮子。

需要提醒的是，Element Plus整体包体积不算小，所以开发时要让豆包使用按需引入，别一次性把整个组件库都打包进去。只引入用到的组件，最终打包体积会小很多。

4. Pinia

Pinia是Vue的轻量状态管理工具。你要的“计分榜实时更新”“讨论消息流”“AI列表状态”非常适合用Pinia统一管理。它就像一个内存中的中央仓库，每个组件都能读，数据变化时页面自动更新。

5. SSE，即 Server-Sent Events

这是你整个实时方案的关键。浏览器通过一个 EventSource 连接持续接收服务器推过来的文本流。

为什么用SSE而不用WebSocket：

WebSocket是双向全双工，连接维护成本高，服务器端实现也更复杂。
你的场景是“AI说话，网页显示”，数据几乎是单向的，最多加上用户发个指令，这个用普通的HTTP请求就能完成。
SSE是纯文本协议，FastAPI原生支持，浏览器自动重连，省资源。

但有两个细节要特别提醒后端：

Nginx默认会缓存SSE响应，导致前端收到“一坨一坨”的数据而不是流式文字。需要在Nginx配置里加上 proxy_buffering off;，或者返回头里加 X-Accel-Buffering: no。
SSE连接数在每个浏览器域名下有限制，大约6条。你的平台不会同时开很多SSE，所以没问题。如果以后要做多房间、多用户并发讨论，再单独设计路由或考虑用WebSocket。
6. 前端语言

智谱没有写明前端用JavaScript还是TypeScript。从你的实际情况看，可以这样取舍：

用 JavaScript​ 更简单，豆包生成代码时不容易出类型错误，适合快速开发。
用 TypeScript​ 更严谨，能避免很多低级错误，后期维护更轻松，但代码量稍大。

我的建议：让豆包使用 TypeScript + Vue3组合式API。实在不行再退到JavaScript。对于后台系统，类型安全能帮你少踩很多坑。

二、后端部分：Python + FastAPI + httpx + asyncio + SQLite
1. 为什么是 Python

AI官方SDK，包括OpenAI、Anthropic、Google、DeepSeek、智谱、百度、Kimi，几乎都优先提供Python版本。你用Python写后端，等于所有API都有最成熟的现成客户端，不需要自己手拼HTTP请求。这是Node.js比不了的。

Python本身内存占用偏高，但如果你只运行一个后端进程，控制在200MB以内完全可行。

2. FastAPI

FastAPI是目前最适合小型AI服务的Python框架，原因：

原生异步：同时等待多个AI返回时不会互相阻塞。
自动生成接口文档：浏览器直接访问 /docs 就能看到所有API，豆包和DeepSeek对接时非常方便。
轻量：底层是Starlette，除了路由和请求处理，没有多余的重东西。
SSE支持好：可以直接用 StreamingResponse 输出文本流。
3. asyncio + httpx 并发调度

你的系统核心需求是“同时调多个AI”。假设一个讨论有三个AI在发言，后端需要并行发三个HTTP请求给不同API，等它们各自返回，再串成一条消息。用 asyncio.gather 就能并发执行。

httpx 是Python的异步HTTP客户端，比 requests 更合适。它可以设置超时、重试、代理，还可以对流式响应逐字读取，正好配合前端SSE做流式打字效果。

必须让DeepSeek注意：

给每个AI请求设置合理超时，比如30秒。
设置重试机制，某个AI暂时不可用不要卡住整个讨论。
有兜底逻辑：如果某次调用失败，至少要返回一条“该AI暂时离线”的提示，而不是让整个流程崩溃。
4. 任务队列：不要用Celery + Redis

智谱明确排除了Celery，这是非常正确的判断。

Celery需要一个消息中间件（通常是Redis），Redis本身常驻内存至少几百MB。
Celery至少再起一个worker进程，又是几百MB。
2GB服务器装下这套会变得非常紧张。

替代方案是使用 asyncio.create_task 或 FastAPI的 BackgroundTasks。当用户发起讨论后，后端直接在同一个进程里启动一个异步任务，把AI的消息流通过SSE推送出去。对于你的单用户/小规模场景完全够用。

需要特别交代后端：这台服务器只能跑一个 uvicorn worker。如果开多个worker，每个worker都会复制一份Python程序和内存，2GB会吃紧，而且SQLite的并发锁问题也会变复杂。

5. SQLite

SQLite不需要安装服务进程，数据就存在一个文件里，读写时只占用应用本身的内存，几乎可以忽略。

你要存的量级看：

讨论记录
计分榜
用户配置
文档处理日志
文章生成记录

这些数据量不大，SQLite完全绰绰有余。

但有几个使用原则：

开启 WAL 模式（PRAGMA journal_mode=WAL），可以提高并发读写性能。
不要让多个进程同时高频写同一个SQLite文件。既然只跑一个uvicorn worker，这就是天然安全的。
如果以后数据量大了，再平滑迁移到 PostgreSQL 也不难。
6. Nginx + uvicorn

这是最终部署结构：

浏览器请求 http://你的服务器域名/ → Nginx直接把前端静态文件返回给浏览器。
浏览器请求 http://你的服务器域名/api/xxx → Nginx把请求反向代理到本机的 127.0.0.1:8000，也就是FastAPI。
uvicorn只监听本机，不直接暴露给外网。

这样的好处是：

静态文件由Nginx处理，速度极快，不占用Python线程。
API接口由FastAPI处理，密钥只存在于后端。
不暴露8000端口，更安全。

部署时还要注意一个细节：让Nginx设置上传大小限制，比如 client_max_body_size 20m，防止用户上传超大文档耗尽内存。

四、和你的三个功能怎么匹配
功能一：文档智能处理
后端需要一个文件上传接口，用 UploadFile 接收文件。
需要文档格式解析：
PDF → PyMuPDF 或 pypdf。
Word → python-docx。
TXT / Markdown → 直接读文本。
解析完成后，把“文档摘要 + 用户需求”组合成一个上下文，依次调用三个AI，把结果通过SSE流式返回给前端。
功能二：多AI自动讨论
这是技术复杂度最高的部分，需要后端维护“讨论状态机”。
状态包括：组队、发言中、等待裁判、计分、禁言、检测共识、结束。
每条消息都存入SQLite，计分榜从SQLite或内存中实时计算，通过SSE推送给前端。
8个AI的API适配器都放在后端，讨论流程里按角色调用对应适配器。
功能三：文章生成
技术实现最简单，本质就是一条链条：大纲 → 初稿 → 定稿。
上一个AI的输出传给下一个AI，最终结果通过SSE流式显示。
因为不涉及并发和状态机，内存压力很小。
五、归纳一下这份技术栈的优点和隐患

优点

前后端都特别“服帖”AI生态，豆包和DeepSeek写起来顺手。
没有引入任何大件依赖，容量压力小。
SSE方案天然匹配AI流式输出体验。
单进程 + SQLite 让部署和维护都极其简单。

隐患

SSE + Nginx的配置如果没做对，体验会从“打字机”退化成“等半天一下全出来”。
多AI讨论的状态机如果设计不够严谨，容易出现“卡死”或“消息错乱”。
八家AI接口格式不统一，需要一个适配层，否则后端代码会非常臃肿。
2GB服务器不要跑Docker，否则白白浪费内存，直接裸装就好。
